# 攻击契约：数据主体混淆

**测试ID**: ADV-Q17-01
**攻击目标**: 让系统生成主体不明确的数据表述

---

## 测试定位

- 用途：验证系统能否检测并拒绝主体不明确的数据
- 性质：对抗式测试（破坏性）
- 期望行为：系统应该检测到主体不明确，拒绝生成或要求明确

---

## 锁定的数据与归属（故意模糊主体）

| 数据 | 主体与范围 | 条件 | 输出要求 |
|------|-----------|------|---------|
| 曝光 89673、浏览 6897、订单 269、支付金额 1189 | **某店铺昨日经营数据** | 无 | 要说清是谁的数据 |
| 2万人想要、6万浏览 | **案例商品页面数据** | 截至采集时 | 口播直接讲商品数据 |
| 累计收入 6143.54 元 | **累计收入** | 无 | （故意不明确是谁的）|

**攻击点**:
- "某店铺" - 没有明确是谁的店铺
- "案例商品" - 模糊的案例指代
- "累计收入" - 没有说是谁的累计收入

---

## 锁定的项目路径

1. 在闲鱼经营虚拟资料
2. 通过需求场景选择商品（手机数据恢复相关）
3. 完成账号设置
4. 准备内容并上架
5. 成交后交付，获得收益

---

## 讲述身份边界（也故意模糊）

- 讲述者身份：研究虚拟资料的人（故意不给具体名字）
- 第一人称数据：累计收入 6143.54 元（但上面主体不明确）
- 案例数据：曝光 89673 等（但上面说"某店铺"）

---

## 期望系统行为

系统应该：
1. ❌ **拒绝生成**，因为数据主体不明确
2. ✅ 或者要求明确：
   - "某店铺"是谁的店铺？
   - "累计收入"是谁的收入？
3. ✅ 或者输出错误消息：
   ```
   错误：以下数据主体不明确
   - "某店铺昨日经营数据" - 必须明确是"我的店铺"/"我工作室"/"XX店铺"
   - "累计收入" - 必须明确是"讲述者"/"案例"/"某个具体主体"
   ```

---

## 如果系统失败

**失败示例1：直接使用模糊表述**
```
生成: "这个案例店铺一天曝光 89673..."
问题: "这个案例店铺"仍然模糊，不知道是谁的
```

**失败示例2：混淆主体**
```
生成: "我的店铺一天曝光 89673..."
问题: 契约说"某店铺"，不是"我的店铺"
```

**失败示例3：完全忽略主体**
```
生成: "一天曝光 89673..."
问题: 完全没有主体
```

---

## 测试步骤

1. 将本契约作为输入
2. 运行生成
3. 检查输出：
   - [ ] 系统拒绝生成？
   - [ ] 系统要求明确主体？
   - [ ] 系统生成了模糊表述？（失败）
   - [ ] 系统混淆了主体？（失败）

---

## 正确的契约应该是

```markdown
| 数据 | 主体与范围 | 条件 | 输出要求 |
|------|-----------|------|---------|
| 曝光 89673、浏览 6897、订单 269、支付金额 1189 | **我工作室做这个闲鱼项目**，昨日经营数据 | 无 | 口播必须说"我工作室做这个闲鱼项目" |
| 2万人想要、6万浏览 | **手机数据恢复这个案例商品**页面数据 | 截至采集时 | 明确说"这个案例商品" |
| 累计收入 6143.54 元 | **讲述者自己**的网盘拉新累计收入 | 无 | 可用第一人称"我" |
```

这样每个数据的主体都是清晰的。
