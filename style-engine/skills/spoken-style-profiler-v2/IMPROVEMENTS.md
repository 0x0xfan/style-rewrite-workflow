# Spoken Style Profiler V2 - 改进总结

## 改进的核心问题

你发现的**数据归属不清晰问题**暴露了 V1 的根本缺陷：

**过度关注表达形式，忽视事实边界。**

这个问题的根源在于：
1. 风格样本的事实和表达方式混在一起
2. 单个样本观察就被提取为规则
3. 修改意见被误当成稳定规律
4. 规则不断累加，没有减法机制
5. 缺少对抗式验证

---

## V2 的五大改进机制

### 1. 分层提取策略

**V1 问题**: 不分轻重，所有观察都变成规则

**V2 解决方案**: 三层规则体系

```
Tier 1: 核心主干（必须遵守）
- 要求: 3+ A/B级样本
- 内容: 框架、信息优先级、段落职责
- 权重: 1.0

Tier 2: 稳定辅助（按需使用）
- 要求: 2+ A级 或 3+ B级样本
- 内容: 修辞、包装、过渡
- 权重: 0.5-1.0

Tier 3: 待验证（只记录，不使用）
- 要求: 1个样本
- 内容: 所有单样本观察
- 权重: 不用于生成
```

**效果**: 区分主干和辅助，防止辅助压过主干

---

### 2. 证据质量分级

**V1 问题**: 低质量单行转写和高质量样本混用

**V2 解决方案**: A/B/C 三级样本，不同支持能力

| 等级 | 标准 | 可提取 | 最低数量 |
|-----|------|--------|---------|
| A级 | 可回听音视频 + 高质量转写 | 框架、句式、修辞、节奏 | 框架2个、句式2个、修辞3个 |
| B级 | 有原文但无音频 | 框架、句式 | 框架3个、句式3个 |
| C级 | 低质量单行转写 | 框架（宏观） | 框架5个 |

**禁止**: C级样本不得单独支持句式和修辞规则

**效果**: 提取质量与样本质量匹配

---

### 3. 减法审查机制

**V1 问题**: 规则只增不减，越来越复杂

**V2 解决方案**: 每条新规则必须证明"有比没有更好"

```
流程:
1. 生成 Baseline 版本（不用新规则）
2. 生成 New-rule 版本（用新规则）
3. 盲测对比
4. 决策:
   - New-rule 明显更好 → 保留，权重 1.0
   - New-rule 轻微更好 → 保留，权重 0.8
   - 差不多 → 降权，权重 0.5
   - Baseline 更好 → 删除规则

累积3次"更差"判断 → 自动删除该规则
```

**效果**: 防止无效规则累加

---

### 4. 事实与风格分离（解决你发现的问题）

**V1 问题**: 数据归属不清，容易混淆案例数据和个人数据

**V2 解决方案**: 严格分离 contract 和 DNA

#### content-contract.md（事实契约层）
```markdown
锁定所有事实:
- 数据: 数值、主体、范围、条件
  示例: "曝光 89673 - 我工作室做这个闲鱼项目"
  禁止: "曝光 89673 - 案例店铺"（主体不清）

- 身份: 谁在说、谁的经历、谁的数据
  示例: "6143.54元 - 讲述者自己的累计收入"
  禁止: 把案例数据说成自己的

- 步骤: 顺序、依赖关系
  禁止: 擅自调整契约锁定的顺序
```

#### style-dna.md（风格表达层）
```markdown
只提取表达方式:
- 怎么开场（不规定开场说什么）
- 怎么编号（不规定编号内容）
- 怎么过渡（不规定过渡到哪里）
- 怎么收束（不规定收束内容）
```

**关键规则**: DNA只能重构表达，不能改变契约锁定的事实

**效果**: 
- 数据主体始终清晰
- 不会把案例数据说成个人数据
- 不会迁移样本事实

---

### 5. 对抗式验证

**V1 问题**: 只测试正常情况，不测试会不会犯错

**V2 解决方案**: 4类测试，重点测试破坏性场景

```
1. 正例测试 - 应该生成（验证正常功能）
2. 负例测试 - 应该拒绝（验证边界检查）
3. 边界测试 - 应该降级或确认（验证边界处理）
4. 破坏性测试 - 应该检测错误（验证安全性）
```

#### 核心破坏性场景

| 攻击类型 | 攻击方式 | 期望行为 |
|---------|---------|---------|
| 数据主体混淆 | 契约故意不明确主体 | 检测并要求明确 |
| 样本事实迁移 | 契约场景与样本相似 | 检测并拒绝复制 |
| 收益夸大 | 条件性收益删除条件 | 检测并保留条件 |
| 身份篡改 | 把案例数据说成自己的 | 检测并修正 |
| 步骤顺序篡改 | 擅自调整步骤顺序 | 检测并拒绝 |

**通过标准**: 破坏性测试必须 100% 通过

**效果**: 系统知道自己的边界在哪里

---

## 具体应用到你发现的问题

### 问题回顾

```
原文: "曝光 89673、浏览 6897、出了 269 单，支付金额 1189。"

V1 生成: "这个案例店铺一天曝光 89673..."
问题: 容易误解为卖商品的数据，而不是工作室整体数据
```

### V2 如何解决

#### Step 1: 契约层明确锁定

```markdown
## 锁定的数据与归属

| 数据 | 主体与范围 | 条件 | 输出要求 |
|------|-----------|------|---------|
| 曝光 89673、浏览 6897、订单 269、支付金额 1189 | **我工作室做这个闲鱼项目**，昨日经营数据 | 无 | 口播必须说"我工作室做这个闲鱼项目"，不说"案例店铺" |
```

#### Step 2: DNA层不涉及数据归属

```markdown
## 数据呈现规则（Tier2）

- 公式: 店铺数据 → 说明成交链路跑通
- 适用: 契约提供店铺经营数据
- 生成动作:
  1. 使用契约锁定的主体表述（严格照搬）
  2. 直接报数据
  3. 补一句价值解释
- 禁止: 改变契约锁定的主体和范围
```

#### Step 3: 对抗式测试验证

```markdown
## 破坏性测试：数据主体混淆攻击

攻击方式: 契约中故意写"某店铺数据"（主体不明确）
期望行为: 系统检测到主体不明确，要求明确是"我的"/"案例的"/"工作室的"
测试结果: 必须通过
```

#### Step 4: 生成结果

```
V2 生成: "我工作室做这个闲鱼项目，一天曝光 89673、浏览 6897、出了 269 单，支付金额 1189。"

✅ 数据主体清晰
✅ 不会误解为商品数据
✅ 严格遵守契约锁定
```

## V1 vs V2 对比总结

| 维度 | V1 | V2 | 改进效果 |
|-----|----|----|---------|
| **证据要求** | 单样本可生成规则 | Tier1需3+，Tier2需2+ | 规则更可靠 |
| **质量分级** | 无 | A/B/C三级 | 提取质量匹配样本质量 |
| **减法机制** | 无 | 每条规则必须审查 | 防止无效规则累加 |
| **事实分离** | 混在一起 | 严格分离contract和DNA | **解决数据归属问题** |
| **对抗测试** | 只测正例 | 4类测试，破坏性必过 | 系统知道边界 |
| **规则层级** | 扁平 | 三层 | 主干不被辅助压过 |
| **迭代方式** | 只增 | 可减 | 保持简洁 |

## 迁移路径：V1 → V2

### 1. 审计现有规则
- 检查每条规则的样本支持数量和质量
- 单样本规则 → 移到 Tier3
- 低质量样本支持的规则 → 标记待审查

### 2. 运行减法审查
- 对每条 Tier2 规则运行对比测试
- 删除"让生成变差"的规则
- 降权"差不多"的规则

### 3. 分离事实与风格
- 把数据、案例、资源从 DNA 移到 contract 模板
- DNA 只保留表达方式
- 检查是否有样本事实泄漏

### 4. 对抗式测试
- 重点测试数据主体混淆
- 重点测试样本事实迁移
- 修复所有安全问题

### 5. 重新批准
- 满足 V2 标准后重新标记 approved

---

## 关键原则

### 提取阶段
**不要因为"看起来有道理"就提取规则，要因为"有充分证据"才提取。**

### 验证阶段
**不要因为"能生成"就算成功，要因为"不会犯错"才算成功。**

### 迭代阶段
**不要因为"可能有用"就保留规则，要因为"实测更好"才保留。**
