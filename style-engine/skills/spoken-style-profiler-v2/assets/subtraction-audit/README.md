# 减法审查流程指南

## 核心原则

**每次添加新规则后，必须证明"有这条规则"比"没有这条规则"更好。**

如果不能证明，删除该规则。

---

## 什么是减法审查

减法审查是一种对比测试方法：

1. 生成 **Baseline 版本**（只用已有规则，不用新规则）
2. 生成 **New-rule 版本**（已有规则 + 新规则）
3. 盲测：评估者判断哪个更像目标风格（不告知哪个是哪个）
4. 决策：保留/降权/删除新规则

---

## 为什么需要减法审查

### 问题1: 规则累加导致过度复杂

```
初版：简洁清晰
↓ 添加规则1
第2版：有所改进
↓ 添加规则2
第3版：稍显复杂
↓ 添加规则3
第4版：开始臃肿
↓ 添加规则4
第5版：完全不像原风格了
```

### 问题2: 修改意见被误当成稳定规律

```
用户反馈："这个地方可以加个承接"
↓
提取为规则："每个段落必须有承接"
↓
生成变成说明书，满篇都是"接下来、然后、下面"
```

### 问题3: 辅助控制压过核心主干

```
核心：具体项目 + 数据 + 步骤
↓ 添加"认知包装"规则
变成：满篇"很多人以为...其实...真正关键..."
↓
核心主干被遮蔽
```

## 减法审查流程

### Step 1: 准备测试输入

选择一个有代表性的契约（content-contract.md）：
- 不要太简单（无法体现规则差异）
- 不要太特殊（结果不具普遍性）
- 最好是之前测试过的契约（便于对比）

### Step 2: 生成 Baseline 版本

使用当前已批准的规则（不包含新规则）：

```bash
# 配置：只加载 Tier1 + Tier2（除新规则外）
generate --contract test-contract.md --dna baseline-dna.md --output baseline-output.md
```

**记录信息：**
- 生成时间
- 使用的规则列表
- 生成结果路径

### Step 3: 生成 New-rule 版本

使用当前已批准规则 + 新规则：

```bash
# 配置：加载 Tier1 + Tier2 + 新规则
generate --contract test-contract.md --dna newrule-dna.md --output newrule-output.md
```

**记录信息：**
- 生成时间
- 新增的规则ID
- 生成结果路径

### Step 4: 盲测对比

准备两个版本，**不标注哪个是哪个**：

```
版本A：{baseline-output.md 内容}
版本B：{newrule-output.md 内容}
```

**随机顺序**：用随机数决定 A/B 对应 baseline/newrule

### Step 5: 评估问题

向评估者（可以是用户、另一个 agent、或隔一段时间后的自己）提问：

**问题1: 风格相似度**
- 问：哪个版本更像目标风格？
- 选项：A / B / 差不多

**问题2: 可读性**
- 问：哪个版本更容易理解、更自然？
- 选项：A / B / 差不多

**问题3: 信息清晰度**
- 问：哪个版本把项目、数据、步骤讲得更清楚？
- 选项：A / B / 差不多

**问题4: 整体偏好**
- 问：如果只能保留一个，你会选哪个？
- 选项：A / B

### Step 6: 揭示身份并决策

告诉评估者：A 是 baseline，B 是 newrule（或相反）

**决策规则：**

| 评估结果 | 决策 | 权重 | 说明 |
|---------|------|------|------|
| New-rule 在 3-4 个问题上更好 | 保留规则 | 1.0 | 明显改进 |
| New-rule 在 1-2 个问题上更好，其他持平 | 保留规则 | 0.8 | 轻微改进 |
| 两个版本差不多 | 降权保留 | 0.5 | 可选规则 |
| Baseline 在 1-2 个问题上更好 | 删除规则 | - | 无改进或轻微退化 |
| Baseline 在 3-4 个问题上更好 | 删除规则并记录为反规则 | - | 明显退化 |

### Step 7: 记录结果

在 `subtraction-audit/rule-addition-log.md` 中记录：

```markdown
## 审查记录：{规则ID} - {规则名称}

**审查日期**: {DATE}
**审查人**: {REVIEWER}
**测试契约**: {contract-file.md}

### 对比版本

- Baseline: {路径}
- New-rule: {路径}
- 新规则ID: {规则ID}

### 盲测结果

- 版本A = {baseline/newrule}
- 版本B = {newrule/baseline}

| 问题 | 选择 | 说明 |
|------|------|------|
| 风格相似度 | {A/B/差不多} | {理由} |
| 可读性 | {A/B/差不多} | {理由} |
| 信息清晰度 | {A/B/差不多} | {理由} |
| 整体偏好 | {A/B} | {理由} |

### 决策

- **结论**: {保留/降权/删除}
- **权重**: {1.0/0.8/0.5/-}
- **理由**: {详细说明}

### 后续行动

- [ ] 更新规则权重
- [ ] 更新规则状态（draft → review_only → approved）
- [ ] 如删除，记录到反规则清单
```

## 累积审查规则

### 3次"更差"判断 → 自动删除

如果一条规则在 3 次不同的减法审查中都被判定为"更差"：
- 自动删除该规则
- 记录到反规则清单（避免重复添加）
- 分析失败原因

### 反规则清单

记录那些看起来有道理，但实测会让生成变差的规则：

```markdown
## 反规则：{规则描述}

**曾尝试添加**: {日期}
**删除原因**: {在3次减法审查中均表现更差}

**失败原因分析**:
- {原因1}
- {原因2}

**教训**:
- {学到什么}

**禁止重复添加**: 如果未来又提取到类似规则，需要先查看此记录
```

## 批量规则的减法审查

### 如果同时添加多条规则

**不要一次性测试所有规则**，而是：

1. 先测试核心框架类规则（Tier1 候选）
2. 逐条测试辅助模式规则（Tier2 候选）
3. 每测试一条，立即决策
4. 通过的规则保留，再测试下一条

**为什么不能批量测试：**
- 无法判断是哪条规则带来改进/退化
- 规则之间可能有冲突
- 难以定位问题

## 特殊情况处理

### 情况1: 规则在某些场景下好，某些场景下差

**解决方案：明确适用条件**

```markdown
## 规则：{规则名称}

**适用条件**（通过减法审查的场景）:
- 契约包含 {特征1}
- 内容类型为 {类型}

**不适用条件**（减法审查表现差的场景）:
- 契约缺少 {特征1}
- 内容类型为 {其他类型}
```

### 情况2: 规则效果不稳定

多次减法审查结果不一致：
- 第1次：更好
- 第2次：差不多
- 第3次：更差

**解决方案：降低权重 + 标记为可选**

```markdown
**权重**: 0.5
**状态**: optional（可选规则）
**说明**: 效果不稳定，生成时可选择使用或不使用
```

### 情况3: 评估者意见不一致

两个评估者对同一对比版本给出不同判断：
- 评估者A：New-rule 更好
- 评估者B：Baseline 更好

**解决方案：引入第三方评估**

- 第3个评估者进行盲测
- 采用多数原则
- 如果仍然 1:1:1，标记为"争议规则"并降权

---

## 快速检查清单

在运行减法审查前，快速检查：

- [ ] 新规则有明确的适用/不适用条件
- [ ] 新规则不与已有规则重复
- [ ] 新规则有 2+ 样本支持（Tier2）或 3+ 样本支持（Tier1）
- [ ] 测试契约有代表性
- [ ] Baseline 版本和 New-rule 版本只差一个规则
- [ ] 盲测问题已准备
- [ ] 记录模板已准备

## 常见错误

### 错误1: 跳过减法审查，直接添加规则

**后果**: 规则累加，生成质量下降，不知道是哪条规则的问题

**正确做法**: 每添加一条规则，必须运行一次减法审查

### 错误2: 同时测试多条规则

**后果**: 无法判断是哪条规则带来的改进或退化

**正确做法**: 逐条测试，每次只测一条新规则

### 错误3: 评估时已经知道哪个是哪个

**后果**: 心理预期影响判断（"我期待新规则更好"）

**正确做法**: 真正的盲测，评估前不看标签

### 错误4: 只看"更像"，不看"更清晰"

**后果**: 风格像了，但读者看不懂

**正确做法**: 同时评估风格相似度、可读性、信息清晰度

### 错误5: 保留所有"差不多"的规则

**后果**: 规则臃肿，生成复杂

**正确做法**: "差不多"的规则降权到 0.5，并标记为可选

## 减法审查工具脚本

```python
# scripts/subtraction-audit.py

# 运行方式：
python scripts/subtraction-audit.py \
    --contract tests/test-contract.md \
    --baseline-dna style-dna/baseline.md \
    --newrule-dna style-dna/with-new-rule.md \
    --new-rule-id T2-P05 \

# 自动生成：
# 1. Baseline 版本
# 2. New-rule 版本
# 3. 盲测问卷（A/B 随机）
# 4. 记录模板
```

## 总结

减法审查的核心思想：

**不要因为"看起来有道理"就添加规则，要因为"实测确实更好"才保留规则。**

宁可规则少一点，也不要让无效规则污染档案。
