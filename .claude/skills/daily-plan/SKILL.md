# daily-plan · 今日选题与分派

用户圣矾：做闲鱼虚拟项目的 B 站 UP 主，非技术人员。说大白话、给选项带推荐、一次只问一件事；**选题表用户点头之前一篇都不写**。

本技能由主会话用：主会话只排表、问用户、派 worker、验收、追加共享文件；稿子全部由 worker 按写稿技能写。

## 2. 排「今日选题表」（16 行）

**两条硬规矩（只有这两条）：**
1. **同一账号不重复**：这一行的选题，在台账这个账号那一节里没出现过。
2. **同一天各篇选题不同**：16 行的选题两两不同（同一个品的横版和竖版也不行，当天只能出现一次）。

**排的时候再照顾这几点（不是硬规矩，做不到就在表下说一句）：**
- 横版 6 个账号排产品题（SRT / 素材库 / 选题卡）；竖版、聊天记录、真人出镜可以排知识题。
- 不同账号之间尽量不撞题（DECISIONS：「皮肤与皮肤之间能做到不重复，那是最好的」）：优先挑所有账号都没用过的题，其次挑别的账号用过但本账号没用过的。
- 产品题要有钱数来源：SRT 里用户亲口说过的数，或选题卡上写的数；都没有的题写进表但在「备注」标"缺钱数，要用户补"，或者换题。
- 短视频（竖版六套 + 真人出镜）前两句要有"闲鱼"和一个闲鱼数据（`docs/短视频规格.md`）：排知识题时想好用哪个闲鱼数据（素材库截图 / 以前实搜的截图）；聊天记录讲经验的稿不要求数据（chat-record 第 4 节）。
- 素材库里用户放了图和关键词的品，优先排给横版（素材齐，出片省事）。
- 同一选题今天之前已经写过很多篇的，往后放。

**「选题核心状态」一列（2026-09-29 定，核心卡拆分后新增）：** 每行的选题按第 1 节第 5 条判断——
- **老选题**：`docs/每日/选题核心/<选题>.md` 已存在（或属于 0928 批，判定见 `docs/每日/选题核心模板.txt`）。这一列写"老选题（已确认 <日期>）"，不用再附核心要点，worker 直接读文件写稿。
- **新选题**：没有对应文件。这一列写"新选题"，并在表下面附一张「新选题核心要点」小表，每个新选题 3–5 行：卖什么 / 钱从哪来（有数就写数，没有写"没有收益数"）/ 主推做法（一句话）/ 稿件类型（产品/经验）/ 不能说的或不能讲偏的（有就写，没有留空）。这几行不用查证据、不用出完整选题核心卡，够用户一眼看懂"这个选题打算怎么写"就行；确认后 worker 照这几行扩成完整选题核心卡（daily-write 第 2 节），不再另问用户。

**表的格式（交给用户看的就是这张）：**

| # | 账号 | 选题 | 类型（产品/知识） | 来源（SRT 第 N 期 / 选题卡 / 素材库 slug / 经验库编号） | 该账号用过吗 | 别的账号用过吗 | 选题核心状态 | 备注 |
|---|---|---|---|---|---|---|---|---|
| 1 | 黑黄 横版 | …… | 产品 | SRT 第 47 期 | 没用过 | 没有 | 新选题（要点见下表） | |
| … | | | | | | | | |
| 12 | 真人出镜 3 | …… | 知识 | 经验库 E123 | 没用过 | 竖版对账台 3 天前用过 | 老选题（已确认 2026-09-20） | |

新选题核心要点（表里标"新选题"的每个选题一份，选题名和上表一致）：

| 选题 | 卖什么 | 钱从哪来 | 主推做法 | 稿件类型 | 不能说的/不能讲偏的 |
|---|---|---|---|---|---|

- 「该账号用过吗」一列 16 行都必须是"没用过"，有一行不是就重排。
- 自查一遍"12 个选题两两不同"，在表下写一句"已核对：12 个选题各不相同"。
- 表下最多三行说明：今天为什么这么排（比如用户发了两张选题卡已排进 1、2 行）、哪几行缺钱数、哪几行以前写过同题旧稿。

## 3. 交用户确认（唯一的门，2026-09-29 定：核心要点并进这一道门，不再另开）

把选题表连同「新选题核心要点」小表一起发给用户，问一句："今天这 16 篇按这张表写，新选题的核心要点也一并看一下，可以吗？想换哪行、改哪条核心直接说。"
- 用户改了哪行，以改的为准，改完再核一遍两条硬规矩。
- 用户对某个新选题的核心要点没意见 → 这个选题就算核心已确认，派给 worker 时直接说"选题表确认时已经把核心要点一起过了，直接写，不用再问用户"（worker 照 daily-write 第 2 节把这几行扩成完整选题核心卡存档，不再停下问用户）。
- 用户点头之前：不派 worker、不去闲鱼搜、不写稿。
- **不再单独开"横版核心卡"这道门**（原 09-25 做法，2026-09-29 起并入本节）：新选题的核心已经在这一步过了，老选题本来就不设门；daily-write 第一段（核心卡）这一步对 daily-plan 派的活形同跳过，worker 直接进第二段（查、写、自检、交付）。

## 4. 分批派 worker（用户点头后）

**每个 worker 的派单里写清：** 日期、账号（skin + orientation，或 selfie + 当天序号 01/02/03）、lengthTarget、字数、选题、来源（期号 / 选题卡原文 / 素材库 slug / 经验库编号）、topicSlug、要读的写稿技能、NAS 上这个选题有没有旧稿、交付文件名（第 5 节）、readSet / writeSet / forbiddenPaths、**选题核心状态**（2026-09-29 定，替代原来单独的核心卡批次）：
- **老选题**：写"老选题，选题核心见 `docs/每日/选题核心/<选题>.md`，直接读，不用问用户"。
- **新选题**：把第 2 节「新选题核心要点」小表里这个选题的那一行原样抄给 worker，写"选题表确认时已经把这几行核心要点一起过了，照 daily-write 第 2 节扩成完整选题核心卡存档，不用再停下问用户"。
- **风格号**（对账台 / 蓝图拆解 / 像素街机的横版）：派单里写一行"风格号：<钱十七 / 老王 / 半佛>，照 daily-write 第 5b 节写，原文在 `docs/风格/<风格>/`，样稿在 `docs/风格/<风格>/样稿/`"。同一选题当天派给几个风格号时（跨天同题也一样），各篇照旧不共享故事、例子、自造说法和开头结构；后写的 worker 要看先交的同题稿；选题跟样稿同题的，把样稿也当作以前交过的同题稿。

**writeSet 怎么划（一天 16 篇选题各不相同，所以按选题天然不交叉）：**
- 每个 worker 只写：`research-runs/每日/<YYYYMMDD>-<选题>/`（或它技能规定的 `scratch/…/` 子目录，带选题名）、新选题时的 `docs/每日/选题核心/<选题>.md`（只建/改自己这个选题那一份）、NAS `待审文案\<选题>\` 里自己那几个新文件、NAS `资料\<选题>\`、视频项目该选题的 `_inbox\shot-requests.json`（daily-write 4.2 节）。
- **共享文件 worker 一律不写**（并行写会互相覆盖）：`docs/稿件登记.json`（registry add）、`docs/每日/故事登记.md`、`docs/每日/账号选题台账.md`。worker 在报告里交三样：registry add 的完整命令、故事登记要追加的一行、台账要追加的一行；主会话在第 6 节按顺序一条条执行。
- forbiddenPaths：治理文件（CURRENT / DECISIONS / HANDOFF / 反馈台账 / 稿件登记 / 写稿规则 / 校准词表）、别的选题的文件夹（包括别的选题的 `docs/每日/选题核心/*.md`）、视频仓库除 `_inbox\shot-requests.json` 以外的一切。

**闲鱼实搜和百度采集只能一个一个来**：`topic-scan` / `baidu-demand` 用同一台机器上的采集 Chrome，两个 worker 同时搜会互相抢。派单时写明"要实搜先报给主会话排队"，或者干脆把要实搜的几个选题放进同一批、由一个 worker 依次搜。优先用 SRT 原片截图、素材库和现成截图，少实搜。

**分三批，一批做完验收了再派下一批（不一次派 16 个；2026-09-29 起横版不再单独分核心卡批次，因为新选题的核心已经在选题表那一道门里过了）：**

| 批 | 内容 | worker 数 | 每个 worker 写几篇 | 说明 |
|---|---|---|---|---|
| 1 | 横版 6 篇（查、写、自检、交付，含新选题落核心卡文件） | 3–4 | 各 1–2 篇 | daily-write 完整流程；一个 worker 同一时间只写一个选题（daily-write "一次只做一个选题"） |
| 2 | 竖版六套皮肤 6 篇 | 3 | 各 2 篇 | short-video；可以和批 1 同时跑（选题不同，writeSet 不交叉），但实搜要排队 |
| 3 | 聊天记录 1 篇 + 真人出镜 3 篇 | 2 | 一个写聊天记录，一个写 3 篇真人出镜 | chat-record / short-video（selfie） |

- 同时在跑的 worker 最多 4 个；额度紧就一批一批串着跑。
- 同一个 worker 不同时拿两个技能的活（比如不让一个 worker 既写长稿又写聊天记录）。
- 某个选题查不到数据、缺钱数：worker 停下回报，主会话问用户换题还是补数（一次问一件事），不让 worker 自己换题——换题要重新核两条硬规矩。
- worker 连着失败两次同一件事就停，写进报告，不重试。
- **两个 worker 都分到同一个新选题的不同篇**（比如横版和竖版都排了同一个新选题，虽然当天选题表规矩不允许同题两行，但"别的账号用过吗"那栏可能让同一新选题跨天被两个 worker 先后落核心卡文件）：先落文件的算数，后写的 worker 发现 `docs/每日/选题核心/<选题>.md` 已存在就直接读，不覆盖、不重新问用户。

**worker 报告要有五项**：改动文件（NAS 上新建的文件清单）/ 命令与结果（自检结果）/ 产物路径 / commit（写"无"）/ 剩余风险；外加上面说的三样（registry 命令、故事登记行、台账行）。

## 5. 交付命名和 .meta.json（所有写稿技能统一照这个）

正稿都放 `Z:\素材生成库\ai文案\待审文案\<选题>\`（NAS 同一位置：`\\Zqkj_nas\一楼4t\素材生成库\ai文案\待审文案\<选题>\`），资料放 `资料\<选题>\`。

**中控台「今日任务」怎么读这些文件（2026-09-29 补充，正式说明见视频仓库 `tools/console/API.md`「今日任务」一节，只读）：**
- `skin` **必填**，且必须是注册表 `docs/skins/skins.json` 里 `status:"final"` 的 id：`black-yellow-v2` / `lime-capsule` / `signature-wall` / `ledger-desk` / `blueprint` / `pixel-arcade` / `chat` 这七个（全部已定版）。`orientation` **必填**，只能是 `h` 或 `v`。这两个字段系统真的读，拼错、缺字段都会导致这篇稿配不上任何账号卡片。
- `lengthTarget` / `date` / `topicSlug` / `title` **系统不读**，只供人看——中控台自己按「正文字数 ÷ 4.5 字/秒（1.2x 语速）」估时长，不看 `lengthTarget`。这几个字段照旧写清楚（给人看、给以后扩展用），但错了不影响今日任务卡片，不是硬门槛。
- **真人出镜靠 `kind:"selfie"` 这一个字段区分**（不是"没写 skin 就当真人出镜"）：必须显式写 `"kind":"selfie"`，`orientation` 固定 `"v"`；这类稿永远不进渲染/出片链，不写 `skin`、不写 `topicSlug`。
- **`skin` 拼错，或这个账号的 `<skin>-<orientation>` 组合中控台还没接入出片链**（现状 2026-09-29：`black-yellow-v2` / `signature-wall` / `ledger-desk` 三个皮肤的竖版 `v` 还没在 `docs/skins/skins.json` 登记 `orientations` 字段，只有横版 `h` 能配上账号卡片；`lime-capsule` 横竖都已接入；`chat` 只有竖版；2026-09-30 起 `blueprint` / `pixel-arcade` 横竖都已接入出片链），**都不会报错**，这篇稿会安静地落进中控台「未分配」池，交付时不知道。所以**每篇交付前自查一遍**：`skin` 拼写和上面七个 id 完全一致、`orientation` 是不是这个账号真支持的画幅；发现某个账号的 `v` 还没接入出片链，仍按 daily-plan 排的账号正常写、正常交付（稿子先存着，等中控台接入这个组合就能用），但在回报里提醒一句"这篇当前进不了未分配以外的池，等 `<skin>` 的 `v` 出片链接入"。
- **中控台用正文内容的哈希当这篇稿的键**（挪目录、改文件名都不影响识别，但正文一字不差就会被当成同一篇）：**同一天交付的多篇正稿正文不能完全相同**——本来"同题各篇不共享故事/例子/开头结构"这条硬规矩已经保证了这一点，这里只是提醒 worker 写完后扫一眼，别把长稿和短稿、或者两个账号的稿写成一字不差（比如偷懒直接复制一份）。

| 账号 | 正稿文件名 | 旁边的 .meta.json |
|---|---|---|
| 皮肤稿（横版/竖版） | `<YYYYMMDD>-<选题>-<skin>-<h\|v>.txt` | `<YYYYMMDD>-<选题>-<skin>-<h\|v>.meta.json` |
| 聊天记录 | `<YYYYMMDD>-<选题>-chat-v.txt` | `<YYYYMMDD>-<选题>-chat-v.meta.json` |
| 真人出镜 | `<YYYYMMDD>-<选题>-selfie-<NN>.txt`（NN = 当天第几篇真人出镜，01/02/03） | `<YYYYMMDD>-<选题>-selfie-<NN>.meta.json` |

- `.meta.json` 和正稿**同名、只换扩展名**（`xxx.txt` 配 `xxx.meta.json`，不是 `xxx.txt.meta.json`）——中控台「今日任务」就是按这个把稿子配到账号卡片上的。
- 皮肤稿的 `.meta.json`（UTF-8，不带 BOM）：
  ```json
  {"skin":"black-yellow-v2","orientation":"h","lengthTarget":"5min","date":"2026-09-29","topicSlug":"jiakao-ziliao","title":"驾考资料"}
  ```
  - `skin` 只能是 `black-yellow-v2` / `lime-capsule` / `signature-wall` / `ledger-desk` / `blueprint` / `pixel-arcade` / `chat`，拼错了中控台配不上账号、也不报错（见上）。
  - `orientation`：横版 `h`，竖版和聊天记录 `v`。`lengthTarget`：横版 `5min`，竖版 `1-2min`（系统不读，纯供人看）。`date`：写稿当天。
  - `topicSlug`：素材库 slug；素材库还没有这个品就**不写这个字段**（不编 slug）。`title` 可选，写选题名。
- 真人出镜的 `.meta.json`：
  ```json
  {"kind":"selfie","orientation":"v","lengthTarget":"1-2min","date":"2026-09-29","title":"新手标题怎么写才搜得到"}
  ```
  不写 `skin`，不写 `topicSlug`。
- 同名 `.素材.md`（`<同一个文件名去掉 .txt>.素材.md`）照旧可以放在正稿旁边（真人出镜不用放）；说明.md、截图、字幕等其他资料放 `资料\<选题>\`。
- 文件名开头不能是下划线；同名文件已存在就在末尾加 `-2`，不覆盖。
- 写 `.meta.json` 用 node（`JSON.stringify` 后 `fs.writeFileSync(…, 'utf8')`），不要手敲，写完用 `node -e "JSON.parse(require('fs').readFileSync(process.argv[1],'utf8'))" <文件>` 验一遍能解析。

## 6. 汇总（每批 worker 回来后，主会话做）

1. **验收**：看 worker 报告五项；抽查每个选题文件夹里正稿、`.meta.json` 都在、两者同名；打开 `.meta.json` 核一遍 `skin`（五个 id 之一，拼写一致）/ `orientation`（`h`/`v`，和账号对得上）和账号对得上——这两个字段系统真读，错了这篇稿会安静进「未分配」池（第 5 节）；`lengthTarget` 系统不读，看着大致对就行；数一下字数在范围里（横版 1300–1600，竖版 300–600）；扫一眼今天交付的几篇正文，确认没有两篇一字不差（中控台按正文哈希去重，见第 5 节）。
2. **登记**（按顺序一条条跑，不并行）：
   - `node engine/return/registry.mjs add …`：worker 给的命令。账号信息写在 `--note` 里（registry 没有 skin 字段，不改代码），格式固定：
     ```
     --note "写稿模型 <模型>；<长稿|短稿|聊天记录|真人出镜>；账号 <skin>-<h|v>（真人出镜写 selfie-<NN>）；lengthTarget <5min|1-2min>；<讲法/骨架>；NAS <正稿完整路径>"
     ```
     `--id` 用正稿文件名去掉 `.txt`（如 `20260929-驾考资料-black-yellow-v2-h`、`20260929-标题怎么写-selfie-01`）；`--film` 用 topicSlug（素材库没有就用选题拼音，小写连字符；聊天记录照 chat-record 的 `<拼音>-<两位序号>`）。
   - `docs/每日/故事登记.md` 末尾追加 worker 给的行（长稿必有；短稿、真人出镜、聊天记录用了来之不易故事才有）。
   - `docs/每日/账号选题台账.md`：在对应账号那一节表格末尾追加一行（日期｜选题｜topicSlug｜稿件文件名｜存稿），只追加不改旧行。
3. **回报用户**（大白话，一张表）：账号｜选题｜文件名｜字数｜检查结果｜要用户看的事（缺数、待打码的图、待补截图的搜索词）。最后一句告诉用户去中控台「今日任务」逐套审。

## 你不做的事

- 用户没点头就派 worker 或写稿。
- 自己写稿（主会话只排表、派活、验收、登记）。
- 改台账旧行（只有「存稿 → 已发」由主会话或用户按用户说的改）；改 DECISIONS / HANDOFF / CURRENT（需要记的新决定交主控会话）。
- 动视频仓库（只读；唯一例外是写稿技能里规定的 `_inbox\shot-requests.json`）。
- 为了凑满 16 行编选题或编数：选题池真凑不出来，就少排几行，告诉用户缺几篇、为什么。
